## Architecture Decision 1

- **Failure:** FC-010: assistant playback cuts itself off and triggers another reply. The field record counts nine playout barge-ins in about 16 seconds, including after server generation ended. FC-001's earlier five-second desk echo test is historical, not proof for the later full-duplex path. Current-build acoustic causation remains unproven.
- **Root subsystem:** The local duplex audio front end: `PcmAudioCapture`, `PcmAudioPlayer`, `WebRtcAcousticEcho`/`VoiceAec`, and `nova_aec.cpp`. Server VAD observes the uplink; it cannot repair a missing or temporally incorrect local render reference.
- **Current architecture:** Capture reads 3,200-byte blocks (100 ms at 16 kHz mono PCM16), while native AEC splits them into 160-sample blocks. Playback submits 10-ms slices to AEC immediately before AudioTrack writes. The native bridge directly accesses AEC3 AudioBuffer channels, resamples render audio to 16 kHz, and estimates stream delay using playout depth plus a capture-buffer-capacity heuristic. Capture gain and the uplink gate follow AEC. Native availability suppresses Android AEC/NS, which is the correct single-backend direction. However, an empty native result currently falls back to raw capture even when the native framer merely needs more samples. The 16-kHz render path clears leftovers on repeated calls because resampler absence is mistaken for uninitialized state. These are source-confirmed contract defects; their contribution to the recorded older-APK loop has not been measured.
- **Reference architecture:** Official WebRTC [AudioProcessing two-stream contract](https://webrtc.googlesource.com/src/+/refs/heads/main/api/audio/audio_processing.h), `ProcessStream`/`ProcessReverseStream`; [AudioBuffer::CopyFrom](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_processing/audio_buffer.cc); and [EchoCanceller3](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/audio_processing/aec3/echo_canceller3.cc). These establish the reference boundary, not a requirement to install the PeerConnection/network stack. Official upstream takes precedence over the Enaium/webrtc-aec3 extraction used by this repository.
- **Critical difference:** **CURRENT** — internal 10-ms arithmetic wrapped in bursty capture, ambiguous pending-output fallback and incomplete stream continuity. **REFERENCE** — an explicit two-stream processing contract close to the device boundary. **DIFFERENCE** — processing cadence, sample continuity and reference timing must agree end to end; an AEC library symbol being present is insufficient. **FAILURE MECHANISM** — unprocessed residual echo or misaligned reference can reach server VAD and initiate a false driver turn. This is an architectural risk established by code, not a retrospective proof of every FC-010 event.
- **Architecture decision:** Preserve the existing upstream AEC3 algorithm and single local audio seam. Adapt the bridge to the official WebRTC two-stream contract rather than introduce a second echo suppressor or migrate the entire voice stack. Use true 10-ms capture processing, with any Flex packet aggregation downstream and expressed in elapsed samples/time rather than callback count. Keep exactly one stateful render resampler/framer per stream rate; distinguish pending output from backend failure, never forwarding the same buffered fragment raw and then processed. Base delay on capture/render timing, with an explicitly measured fallback when timestamps are unavailable; do not treat buffer capacity as measured age. Coordinate route/format changes and playback discontinuities with the same AEC session owner. Keep AEC before microphone gain; do not tune thresholds or gain to hide broken reference delivery. Pin the native dependency revision and its provenance before future implementation is accepted.
- **Reuse type:** **B — adaptable subsystem.** Retain AEC3 and adapt its boundary. WebRTC APM is the canonical contract; wholesale APM/ADM or libwebrtc adoption is **D for this bounded repair**, because it adds packaging/JNI/ownership migration without first proving that replacement is necessary. The current extracted bridge is not equivalent to a fully supported public APM integration. WebRTC source carries BSD-style licensing plus PATENTS/AUTHORS obligations; downstream must preserve notices and verify the extraction's revision and dependency licenses, not assume the repository URL is sufficient provenance.
- **Downstream owner:** **GPT-6.0 Astra Low** — sample/clock/JNI ownership needs codebase reasoning. Luna Medium may implement already-specified framing regression cases and dependency-provenance checks afterward.
- **Constraints:** Keep Baidu Flex as the sole speech-to-speech provider; no additional ASR/TTS and no blanket microphone muting during assistant output. Preserve real double-talk. Do not enable platform AEC on top of native AEC without a separately justified backend policy. Crucially, current `WritePcm16ToBuffer` already writes raw PCM16 magnitudes into internal float channels, matching FloatS16 storage; do **not** reapply the earlier normalization fix. The public normalized-float API and internal AudioBuffer channels are different contracts. Acceptance must include playback-only echo rejection, near-end speech, double-talk and route/volume changes on the installed build; RMS reduction alone can also indicate suppression of the driver and is not sufficient.

## Architecture Decision 2

- **Failure:** FC-006 stop-speaking and FC-010 interruptions depend on reliable removal of buffered speech. Playback/capture latency and teardown are shared prerequisites, not separate reasons to replace the speech provider. FC-008 low volume is a related regression constraint, but its existing source fix is not disproved by this review.
- **Root subsystem:** `PcmAudioPlayer` and `PcmAudioCapture` resource ownership, the playout clock, and `LowLatencyPlaybackBuffer`.
- **Current architecture:** Playback frames are epoch-checked only when enqueued, then lose that identity in an unbounded byte-array queue. A worker can hold a slice while another thread clears the queue and calls pause/flush. Partial positive writes are counted but their unwritten suffix is discarded. A final sub-10-ms remainder has no explicit end-of-stream drain. Application-queue drain marks speaking false before the hardware necessarily drains; the later idle fast path can omit the final playback-active notification. Track release precedes worker join, and native AEC destruction follows the core stop path; an unjoined worker must not retain access to released objects. These are static race/accounting findings, not observed crash claims. The custom buffer manager starts at its own minimum floor, cannot shrink below that floor, and ignores the actual size returned by the platform.
- **Reference architecture:** Official WebRTC [WebRtcAudioRecord.AudioRecordThread / stopRecording](https://webrtc.googlesource.com/src/+/refs/heads/main/sdk/android/src/java/org/webrtc/audio/WebRtcAudioRecord.java), [WebRtcAudioTrack.AudioTrackThread / stopPlayout](https://webrtc.googlesource.com/src/+/refs/heads/main/sdk/android/src/java/org/webrtc/audio/WebRtcAudioTrack.java), and [LowLatencyAudioBufferManager.maybeAdjustBufferSize](https://webrtc.googlesource.com/src/+/refs/heads/main/sdk/android/src/java/org/webrtc/audio/LowLatencyAudioBufferManager.java). These supply 10-ms scheduling, urgent-audio threads, bounded joining before release, an optional low-latency track request, and adjustment based on actual buffer size/underruns. For streamed-response semantics, AndroidX Media3 [DefaultAudioSink](https://raw.githubusercontent.com/androidx/media/release/libraries/exoplayer/src/main/java/androidx/media3/exoplayer/audio/DefaultAudioSink.java), especially `handleBuffer`, `drainToEndOfStream`, `hasPendingData` and `flush`, preserves pending output and distinguishes source completion from output completion. Do not claim WebRtcAudioTrack itself retries short writes; that is why Media3 is also consulted.
- **Critical difference:** **CURRENT** — producer completion, application-queue emptiness and acoustic completion are partly conflated; flush races the writer. **REFERENCE** — device-thread lifetime and retained output-buffer progress are explicit, and pending hardware data contributes to completion. **DIFFERENCE** — one ordered output lifecycle must own writes, resets and resource release. **FAILURE MECHANISM** — a stale slice can play after interruption, a partial write can lose speech/reference correspondence, or the assistant can be considered finished while still audible.
- **Architecture decision:** Adapt WebRTC's Android audio-device lifecycle and buffer manager inside the existing ports, with Media3-style retained-buffer/drain accounting. Give the output owner ordered write/flush/close operations and carry reply identity through the last write boundary. A flush must invalidate queued and in-flight work before acknowledging completion. Retain short-write progress; explicitly terminate/pad only the final fragment at response completion, keeping render reference and actual submitted output consistent. Expose one authoritative playout-active state through hardware drain, separate from cloud generation. Bound response buffering with an explicit overflow/cancellation policy, not silent arbitrary PCM loss. Join/quiesce device callbacks before releasing AudioRecord, AudioTrack or native AEC; timeout must not authorize deleting a handle still in use. Use actual accepted buffer sizes and underrun feedback. Request low-latency mode where supported, but measure the result; this app's provider rate/route need not qualify for a fast track. Keep capture/render clock metadata and application queue latency separate; do not add the whole application queue to AEC delay when reference submission occurs at the track boundary.
- **Reuse type:** **B — adaptable subsystem** for WebRTC device scheduling/buffer management; **C — pattern only** for Media3 sink accounting. WebRTC classes depend on its JNI/logging infrastructure and cannot simply be pasted intact. Replacing the PCM port with an entire media player is **D** here. WebRTC BSD-style notices/PATENTS apply; Media3 is Apache-2.0 and any copied implementation needs attribution. No new playback framework is selected.
- **Downstream owner:** **GPT-6.0 Astra Low** — flush, frame identity, native lifetime and focus interact. A bounded port of the settled buffer-size policy can go to Luna Medium after the owner defines the interface.
- **Constraints:** Preserve the single PlaybackPort seam, provider-negotiated sample rates, navigation confirmation/focus policy and FC-008's unducking intent. Do not globally force volume or switch Android audio usage merely to win a latency benchmark. Reconcile AEC gain/discontinuity information with actual playback. Demonstrate no post-flush old audio, no lost final syllable, hardware-tail interruption and repeated safe restart on the device; a source-string/unit guard does not establish these behaviors.

## Architecture Decision 3

- **Failure:** Owner spreadsheet item 9: after sleep, saying the wake phrase does not wake the assistant. No separate FC number is present in the reviewed local register. This blocks a no-touch repeatable demo.
- **Root subsystem:** The boundary between `ListeningLifecycle`, `VoiceSessionGateway`, `WakeWordController` and microphone ownership—not wake-word phrase recognition itself.
- **Current architecture:** SLEEP keeps the Flex connection/session alive but calls `setCaptureSuspended(true)`, stopping conversational capture. Meanwhile `WakeWordController.syncLocked` disables its detector and idle capture whenever `VoiceSessionGateway.isActive` is true. Consequently the sleeping, connected session has neither conversational capture nor wake capture. Its 1.5-second reconciliation loop repeats the same wrong predicate. `VoiceSessionGateway.start` already supports reactivating a healthy sleeping session and replacing a failed session; preserve that behavior. Separately, wake capture failure currently logs an error without clearing the non-null ownership field, which can prevent retry.
- **Reference architecture:** AOSP [SoundTriggerHelper.updateRecognitionLocked](https://android.googlesource.com/platform/frameworks/base/+/master/services/voiceinteraction/java/com/android/server/soundtrigger/SoundTriggerHelper.java), `ModelData` requested/started state and `isRecognitionAllowed`. The helper reconciles desired recognition and eligibility against actual resource state under one owner. It also distinguishes a loaded model from a started recognizer. Its system-server/DSP implementation is not an app-level replacement for this repository's app-fed iFlytek detector.
- **Critical difference:** **CURRENT** — socket/session existence is treated as microphone ownership and proof that the assistant is listening. **REFERENCE** — desired recognition, permission/device eligibility, and actual started state are distinct. **DIFFERENCE** — a live connection does not imply an active capture consumer. **FAILURE MECHANISM** — SLEEP preserves the connection while both potential wake input paths are disabled. This mechanism is directly supported by the inspected branches; recognition quality still needs a device check after correction.
- **Architecture decision:** Keep `ListeningLifecycle` as the policy authority and adapt AOSP's desired-versus-actual reconciliation pattern in the existing wake/session owners. Derive capture ownership from conversational state and actual capture health, not `isActive`. ACTIVE/SILENT_WAIT use conversational capture; SLEEP/DEEP_IDLE use local wake-only capture when enabled, permitted and the app is eligible to record. Transfer the microphone exclusively: stop and quiesce the old owner before starting the new one. Reconcile promptly on lifecycle/permission/error transitions; retain the existing periodic pass only as recovery, using the same reconciliation function. Clear failed actual-resource ownership so bounded retry is possible. On a wake event, disarm wake capture before invoking the existing gateway: resume the healthy SLEEP session, create a new DEEP_IDLE session, or rebuild a failed one. No second lifecycle machine and no new wake SDK.
- **Reuse type:** **C — architecture/pattern only.** AOSP source is Apache-2.0. Direct reuse of SoundTriggerHelper is **D**: hidden APIs, system privileges, DSP models and platform dependencies do not match this app. The existing iFlytek SDK/model and credential contract remain intact.
- **Downstream owner:** **GPT-6.0 Astra Low** — cross-owner transition ordering and error recovery need reasoning. Luna Medium can implement bounded state-matrix checks once the transition contract is settled.
- **Constraints:** SLEEP must send no conversational microphone audio to the cloud. Local wake-only capture is necessary and is already the product's stated intent; the current comment claiming that nothing is captured in SLEEP is too broad and should be corrected only in a future authorized implementation. User-disabled wake and denied permissions must remain disabled. One recorder at a time, one detector listener, no busy retry, no leaked native handle, and no stale wake event reactivating a newer disabled state. Prove repeated ACTIVE → SLEEP → wake → ACTIVE and DEEP_IDLE/error recovery through the actual microphone, not only injected wake clips. Decisions 1–2 govern shared capture/AEC resource safety during handoff.

## Architecture Decision 4

- **Failure:** FC-006: a spoken stop must cut off output while retaining the ability to hear the next command. FC-010: residual echo creates false interruptions and sometimes another reply. A tool-description/unit-test fix for the stop phrase does not establish mid-speech microphone success.
- **Root subsystem:** Acoustic speech qualification (`SpeechUplinkGate`), provider event adaptation (`BaiduFlexClient`), the ingress `VoiceSessionController`, and the existing `DriverTurn`/listening-control owners. These responsibilities must cooperate without becoming one undifferentiated stop flag.
- **Current architecture:** Server speech-start opens a DriverTurn in BaiduFlexClient. In ingress, speech-start while playback is active calls a qualification callback and may flush playback; generation state independently controls remote cancellation. That generation/playout distinction is valuable and must stay. However `AecMetrics.shouldFlushBargeIn` uses the latest post/raw RMS ratio, with no utterance identity or timestamp, to reject interruptions below 0.5. That cannot distinguish successful echo removal with simultaneous quiet driver speech from echo-only input. Rejecting the local flush also does not undo the provider-side turn already opened. `cancelCurrentResponse` flushes locally and invokes cancellation asynchronously. Existing listening policy distinguishes SHUT_UP/SILENT_WAIT from SLEEP, while some stop wording intentionally goes through the Flex tool.
- **Reference architecture:** LiveKit Agents [SpeechHandle.interrupt / wait_for_playout](https://raw.githubusercontent.com/livekit/agents/main/livekit-agents/livekit/agents/voice/speech_handle.py) and [AgentActivity.interrupt and realtime reply handling](https://raw.githubusercontent.com/livekit/agents/main/livekit-agents/livekit/agents/voice/agent_activity.py): speech identity, generation interruption, output-buffer clearing and completed playout are separate concerns. For local acoustic classification, official WebRTC [WebRtcVad_Process](https://webrtc.googlesource.com/src/+/refs/heads/main/common_audio/vad/include/webrtc_vad.h) accepts supported short PCM frames and reports speech activity; it does not identify a speaker or cancel echo.
- **Critical difference:** **CURRENT** — delayed cloud events are qualified with one current energy ratio, while the provider can already open a turn. **REFERENCE** — interruption is attached to a speech instance, with output and generation lifetimes handled explicitly. **DIFFERENCE** — acoustic evidence, interruption acceptance, provider cancellation and semantic intent need distinct contracts and one shared turn identity. **FAILURE MECHANISM** — quiet genuine double-talk can be suppressed, or an echo-triggered cloud turn can survive a local no-flush decision and produce the next audible response. These are source-supported failure mechanisms; their frequency is not established for the new build.
- **Architecture decision:** Preserve the existing ingress session controller as interruption owner and DriverTurn as reply/proof authority. Adopt the LiveKit speech-handle pattern by extending existing turn/playback identities, not adding another framework. Replace the instantaneous attenuation-ratio veto with time-scoped speech evidence produced by the existing uplink gate; use WebRTC VAD as its bounded speech-classification component after AEC, retaining pre-roll/hangover and elapsed-duration accounting. Treat cloud speech-start as a candidate event, not proof of a real driver. Associate qualification and any resulting reply with the same turn; an acoustically unconfirmed turn must not become audible merely because its generated text makes no action claim. Do not mistake VAD for echo rejection: Decisions 1–2 must establish a usable cleaned signal first. Accepted barge-in invalidates local output immediately, including hardware-tail playback after generation ended; cancel the remote response only if still live and supported. Explicit stop-output uses the same output invalidation, enters the existing SILENT_WAIT behavior and continues microphone delivery; stop-listening separately enters SLEEP. Discard late output from the interrupted generation rather than relabel it as the next reply. Keep established local unambiguous commands and model/tool intent handling; no expanding phrase dictionary as the architecture fix.
- **Reuse type:** **C — pattern only** for LiveKit; **A — directly reusable algorithm component** for WebRTC VAD behind the existing gate (native binding still required). LiveKit is Apache-2.0; WebRTC VAD follows WebRTC's BSD-style licensing. Importing LiveKit's Python runtime, its transport, a separate ASR/TTS pipeline or a semantic turn-detection service is **D** for this application. Upstream behavior is a model to adapt, not evidence that Baidu offers the same cancellation/history APIs.
- **Downstream owner:** **GPT-6.0 Astra Low** — provider event ordering, temporal evidence and turn ownership are not mechanical work. Luna Medium can subsequently wire a fixed VAD binding and run bounded event-order checks.
- **Constraints:** No blind timer-based muting, no synchronous network wait before local silence, no losing the next command, and no erasing conversation context just to stop speech. Preserve proof-before-action claims and retain the distinction between real conversational speech and action authorization. Use only confirmed Flex protocol capabilities; if reliable response correlation is unavailable, explicitly quarantine ambiguous old output at the provider seam rather than assume response IDs or truncation commands exist. A stop tool's acknowledgment must not restart unwanted speech. Demonstrate playback-only silence, real double-talk, stop before first audio, stop during the post-generation tail, and a successful subsequent command. Do not advertise a numeric interruption latency until measured on the target device.

## Architecture Decision 5

- **Failure:** FC-009: repeating a displayed POI starts a new search instead of choosing it. The exact-name/汇–滙 path already has a source fix and injected device evidence; do not label that entire fix absent. The unresolved live follow-up requirement includes ordinal selection, alternatives/refinement, and phonetic confusion (owner spreadsheet item 11), which character folding alone cannot solve.
- **Root subsystem:** `EmbeddedNavigationController`/`NavigationStateStore` as the candidate-dialog owner; `NavigationChoiceResolver`, the local picker intercept and dispatcher as its input adapters. The map view and a general prompt phrase list are not the right state owners.
- **Current architecture:** Candidate lists and phase live in the controller, with generation checks on asynchronous search results. `chooseByVoice` supports names, indexes and route preferences. The local utterance intercept only attempts Name; no-match and ambiguity both become null, allowing downstream interpretation as a fresh search. Character matching includes a minimum three-character shared run but no phonetic representation. `NavigationLocalPickGuard` is a process-global one-shot boolean reset by the next transcript, not bound to turn or candidate-list identity. It is marked before the pick callback's result is known, and its consume path can report a local-selection success without carrying that selection's executor result. These are structural limits; no fresh device regression is claimed.
- **Reference architecture:** Microsoft Bot Framework's mature [Prompt.beginDialog / continueDialog](https://raw.githubusercontent.com/microsoft/botbuilder-js/main/libraries/botbuilder-dialogs/src/prompts/prompt.ts) retains prompt options and retries within an active dialog; [ChoicePrompt.onRecognize](https://raw.githubusercontent.com/microsoft/botbuilder-js/main/libraries/botbuilder-dialogs/src/prompts/choicePrompt.ts), [recognizeChoices](https://raw.githubusercontent.com/microsoft/botbuilder-js/main/libraries/botbuilder-dialogs/src/choices/recognizeChoices.ts) and [findChoices](https://raw.githubusercontent.com/microsoft/botbuilder-js/main/libraries/botbuilder-dialogs/src/choices/findChoices.ts) resolve names/synonyms and ordinal/index references against a supplied candidate list. Use this as a reference pattern, not a new SDK dependency. For phonetic features, use Android's public [ICU Transliterator](https://developer.android.com/reference/android/icu/text/Transliterator), grounded in [ICU Transliterator.getInstance](https://raw.githubusercontent.com/unicode-org/icu/main/icu4j/main/translit/src/main/java/com/ibm/icu/text/Transliterator.java) and the [Han-Latin rule source](https://android.googlesource.com/platform/external/icu4c/+/master/data/translit/Han_Latin.txt). The latter illustrates rule-based transliteration, not a guarantee of each target OS's pronunciation data.
- **Critical difference:** **CURRENT** — failure to find one character-based match falls out of the picker context, and deduplication lacks identity and execution evidence. **REFERENCE** — a pending choice retains its candidate set and validates a continuation before ending the dialog. **DIFFERENCE** — unresolved selection is a dialog outcome, not automatically a new destination request. **FAILURE MECHANISM** — an imperfectly recognized candidate name can destroy the list it was meant to reference; a delayed tool can be suppressed under the wrong turn or credited with a selection not yet confirmed.
- **Architecture decision:** Extend the existing navigation owner into an explicit pending-choice context, not a second conversation store. Bind candidate IDs/order, search intent, navigation generation and the current selection turn together. Resolve follow-ups against that snapshot into distinct selection, refinement, new-search, ambiguity and no-match outcomes. Preserve the current canonical select/route methods for both touch and voice. Valid ordinals reference the displayed ordering; refinement modifies the pending search rather than treating every utterance as a new destination; unsupported filters require clarification instead of invented SDK capabilities. Keep the list through clarification and ordinary reply interruptions. Invalidate stale choice authority on replacement/cancel/expiry and session teardown; after sleep, re-present/reconfirm retained navigation options before accepting an old ordinal. Persist here means across turns in the existing controller, not indefinite storage of destination history. Replace the one-shot global suppression flag with turn-and-list-scoped idempotency carrying the actual selection result; report success only after that result exists.

  For phonetic recovery, select ICU-derived candidate pronunciation as a **confirmation aid**, not automatic navigation authority. On supported devices, compare pronunciation within the active candidate set and offer a specific candidate or short shortlist for confirmation; preserve exact/unambiguous matching first. Similar-sounding characters are not necessarily identical pinyin, so transliteration alone is not promised to solve the spreadsheet example. Polyphonic names, weak similarity and ties must clarify. Use a bounded syllable-similarity rule only for ranking confirmation candidates, with thresholds established from the actual candidate examples downstream—not a growing table of misheard place names. When no reliable shortlist exists, ask for an ordinal from the retained list.
- **Reuse type:** **C — architecture/pattern only** for Bot Framework (MIT; no Node runtime or Microsoft cloud dependency). **A — directly reusable platform component** for ICU transliteration where available; no vendored pronunciation corpus is selected. Android documents public Transliterator availability from [API 29](https://developer.android.com/guide/topics/resources/internationalization), but this app has `minSdk = 28`: guard the API and retain ordinal/clarification fallback on API 28 or missing transform data. Do not silently raise minSdk, use hidden APIs, or bundle full ICU4J just for this demo. Any later copying of ICU source/data requires its applicable Unicode/ICU notices; platform API use avoids that packaging change.
- **Downstream owner:** **GPT-6.0 Astra Low** — choice context, asynchronous search generations and exactly-once tool results need reasoning. Luna Medium is suitable for the fixed normalization/API-guard adapter after the owner settles those contracts.
- **Constraints:** One Amap importer and one navigation controller; no UI-owned candidate copy, invented POI, silent ambiguous selection, or tool success inferred from model wording. Keep map and spoken numbering identical. Exact-name/汇–滙 success must not regress. A failed clarification must not discard the current list, while an explicit new destination must not be trapped in it. Do not add separate ASR or log transcripts/addresses/coordinates. Verify live ordinal/name/refinement continuations and delayed stale-tool rejection; injected exact-name success covers only that narrower case.

## Selection Boundary and Handoff

The important architecture choices are complete. Dependency order is **audio lifecycle and AEC boundary (Decisions 1–2) → trustworthy interruption (Decision 4)**. Wake ownership (Decision 3) shares their safe capture teardown contract but does not require a new audio framework. Candidate-dialog ownership (Decision 5) can be developed independently and integrated after voice reliability is demonstrated. This is a dependency statement, not a detailed implementation plan.

Deliberately not selected for redesign:

- **FC-008 volume:** preserve the implemented confirmation-window/unducking policy and verify it audibly alongside Decision 2. The record says FIXED, device verification pending; there is no evidence here justifying a new volume subsystem.
- **FC-007 Amap guidance wording:** OPEN but explicitly non-demo-blocking in the failure register. Its owner is the Amap guidance path, not Flex. No captured boundary evidence distinguishes SDK text, preprocessing or pronunciation; selecting a replacement now would be speculation. Do not follow the local note's suggestion to put raw instructions in ordinary logs; repository privacy constraints still apply.
- **FC-002 help, FC-003 recorded navigation, FC-004 voice persona, FC-005 desk-origin/emulator arrival:** existing fixes or artifacts with narrower verification boundaries, not reasons for architecture churn. Live cabin/real-GNSS or owner review remains distinct from emulator/injected evidence.
- **Transcript overlay polish, rerouting/GPS-loss enhancements and paid traffic-light countdown:** outside this high-impact selection pass. Countdown entitlement cannot be solved by architecture or fabricated simulation.

All references above are primary source/API links inspected for the named behavior. Moving branch links describe the inspected design, not reproducible dependency pins; the implementation owner must pin any copied/vendored revision. No upstream project guarantees success on this device without integration evidence. Repository state refresh, design-basis registration, tests, builds and implementation handoffs are future authorized work—not performed here because only this selection document may change.

Completion: five architecture decisions recorded. No production/source/test/configuration/build edits, no implementation agents, and no implementation performed.
